# คู่มือติดตั้งหมุดกล้อง CCTV สำหรับรู้ทัน

แผนที่สาธารณะแสดงหมุดกล้องและกรวยบอกทิศทางระยะประมาณ 70 เมตร ทั้งใน Leaflet และ MapLibre ใช้ปุ่ม **CCTV** เพื่อแสดงหรือซ่อนหมุด เมื่อเลือกกล้อง ระบบจะเปิดเครื่องเล่นภาพสด HLS สำหรับรับชมเท่านั้น โดยมีปุ่มเล่น/หยุดชั่วคราวและปรับเสียง กรวยใช้บอกทิศทาง ไม่ใช่พื้นที่รับภาพจริงที่ผ่านการวัด

เปิด **Admin → CCTV** หรือ `/admin/cameras` เพื่อจัดการกล้องและดูภาพได้สูงสุด 9 กล้องต่อหน้า API สำหรับจัดการกล้องต้องใช้บัญชีในฐานข้อมูลที่ยังใช้งานอยู่และมีบทบาท `admin` บัญชีผู้ตรวจสอบเนื้อหา (`moderator`) และบัญชีสำรองแบบเดิม `env-admin` ไม่สามารถจัดการกล้องได้ ให้เข้าสู่ระบบด้วยบัญชีผู้ดูแลจากฐานข้อมูล และตั้งค่า `JWT_SECRET` ให้เรียบร้อย

## โครงสร้างการเชื่อมต่อ

กล้อง → โปรแกรม Relay ที่ใช้ Node/FFmpeg ในเครือข่ายเดียวกับกล้อง → ส่ง RTSP ออกผ่าน VPN ส่วนตัว → MediaMTX → ตัวกลาง HLS ภายในระบบ → nginx สาธารณะที่ `/streams/…` → เบราว์เซอร์

กล้องทุกประเภท รวมถึงกล้อง LAN และ ONVIF ใช้ Relay เป็นตัวส่งภาพออกไปยังเซิร์ฟเวอร์ MediaMTX จะไม่ได้รับที่อยู่หรือรหัสผ่านของกล้อง และจะไม่เริ่มเชื่อมต่อเข้าไปในเครือข่ายกล้อง ระบบใช้ ONVIF สำหรับค้นหากล้อง ส่วนการส่งภาพยังต้องระบุ RTSP path ของกล้องด้วย Relay จะแปลงวิดีโอเป็น H.264 และแปลงเสียงเป็น AAC หากมีเสียง

## การติดตั้งระบบ

สิ่งที่ต้องเตรียม: Docker Compose, PostgreSQL ที่ติดตั้ง PostGIS, บัญชีผู้ดูแลในฐานข้อมูล, จุดรับการเชื่อมต่อสาธารณะที่รองรับ HTTPS และ VPN ส่วนตัวระหว่างเครื่อง Relay ระยะไกลกับเครื่อง MediaMTX ไฟล์ Compose ที่มีอยู่เปิดให้บริการผ่าน HTTP จึงต้องตั้งค่าจุดรับ HTTPS/TLS ก่อนเชื่อมต่อ Relay จากระยะไกล

1. ตั้งค่า `DATABASE_URL` หรือข้อมูลเชื่อมต่อฐานข้อมูลที่ระบบใช้อยู่ รวมถึง `JWT_SECRET` สร้างคีย์ลับขนาด 32 ไบต์ **3 ค่าที่ไม่ซ้ำกัน** โดยรันคำสั่งต่อไปนี้แยกกันสามครั้ง:

   ```sh
   node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
   ```

   นำแต่ละค่าไปกำหนดให้ `CCTV_ENCRYPTION_KEY`, `CCTV_CONTROL_TOKEN` และ `CCTV_EDGE_TOKEN` ในตัวแปรสภาพแวดล้อมของระบบที่ติดตั้ง เก็บคีย์เข้ารหัสไว้ในระบบจัดการความลับ หากเปลี่ยนคีย์โดยไม่ได้เข้ารหัสข้อมูลเดิมใหม่ ระบบจะอ่านการตั้งค่ากล้องเดิมไม่ได้

2. ใช้ฐานข้อมูลที่ต้องการติดตั้ง แล้วรันคำสั่งนี้จากโฟลเดอร์ `server` เพื่อปรับโครงสร้างฐานข้อมูลด้วย migration `004_cctv_pins.sql`:

   ```sh
   npm run db:migrate
   ```

   ระบบจะไม่รัน migration ให้อัตโนมัติเมื่อเริ่มแอป

3. รันคำสั่งต่อไปนี้จากโฟลเดอร์หลักของโครงการ เพื่อตรวจสอบการตั้งค่าและเริ่มบริการ:

   ```sh
   docker compose -f docker-compose.production.yml -f docker-compose.cctv.yml config --quiet
   docker compose -f docker-compose.production.yml -f docker-compose.cctv.yml up -d --build
   ```

   ไฟล์ Compose เสริมจะเปิด `CCTV_ENABLED=true` และเพิ่มบริการ MediaMTX กับตัวกลาง HLS ภายในระบบ หากเป็นฐานข้อมูลใหม่ที่ทำงานใน Docker ให้เริ่มบริการ `db` ก่อน แล้วรันคำสั่งนี้ก่อนเริ่มแอป:

   ```sh
   docker compose -f docker-compose.production.yml -f docker-compose.cctv.yml run --rm app node server/db/migrate.js up
   ```

4. หากใช้ Relay ระยะไกล ให้ตั้ง `CCTV_INGEST_BIND` เป็น **IP ของอินเทอร์เฟซ VPN ส่วนตัวบนเครื่อง MediaMTX** ค่าเริ่มต้น `127.0.0.1` ใช้ทดสอบภายในเครื่องเท่านั้น อย่าเปิดพอร์ต RTSP ที่ไม่ได้เข้ารหัสสู่อินเทอร์เน็ตโดยตรง ส่วนพอร์ต HLS 8888 และพอร์ตควบคุม 9997 ไม่ได้ถูกเปิดออกมาที่เครื่องโฮสต์

5. ให้การเข้าถึงแอป, `/api/` และ `/streams/` ผ่าน nginx สาธารณะ หากแยกโฮสต์ frontend และ backend ให้ `VITE_API_URL` ชี้มาที่ nginx นี้ ไม่ใช่ Express โดยตรง ตั้ง `CCTV_PLAYER_ORIGIN` ให้ตรงกับ origin ของ frontend ซึ่งประกอบด้วยโปรโตคอล โฮสต์ และพอร์ตถ้ามี เพื่ออนุญาต HLS ผ่าน CORS หากใช้ origin เดียวกันให้เว้นว่าง อย่าวางแคช CDN ที่ไม่ตรวจสอบสิทธิ์ไว้หน้า `/streams/`

ใช้ Node เวอร์ชัน 20 ขึ้นไปสำหรับ backend และ Relay หากไม่ได้ใช้ไฟล์ Compose เสริม ค่าเริ่มต้นของ `CCTV_ENABLED` จะเป็น false และ API ของ CCTV จะตอบกลับ 503 จนกว่าจะตั้งค่าเสร็จ ฟีเจอร์เดิมของแอปยังทำงานได้ตามปกติ

Vite proxy ยังคงชี้ไปที่ API เดิมบนโฮสต์เป็นค่าเริ่มต้น หากต้องการทดสอบในเครื่อง ให้ตั้งค่าต่อไปนี้ใน `client/.env.local` เพื่อเชื่อมต่อผ่าน nginx ในเครื่อง โดย `/streams` จะถูกส่งต่อพร้อมกับ `/api`:

```text
VITE_PROXY_TARGET=http://localhost
```

ค่าที่ใช้ตอนบิลด์ frontend ต้องอยู่ใน `client/.env` หรือส่งให้กระบวนการบิลด์โดยตรง การตั้งไว้เฉพาะสภาพแวดล้อมของเซิร์ฟเวอร์ไม่เพียงพอ

## การจับคู่ Relay

1. เปิด **Admin → CCTV** แล้วเพิ่มกล้อง โดยระบุพิกัดบนแผนที่, IP, RTSP path เช่น `/stream1`, ประเภทการเชื่อมต่อ และข้อมูลเข้าสู่ระบบกล้อง พอร์ต RTSP เริ่มต้นคือ 554 การบันทึกข้อมูลจะยังไม่เผยแพร่ภาพ จนกว่าจะยืนยันทั้งการตรวจสอบและความยินยอมของเจ้าของ

2. กด **จับคู่ Relay** แล้วคัดลอก `pin_id` และ `relay_token` ที่แสดงตอนจับคู่ไปยังเครื่อง Relay โทเคนจะแสดงเพียงครั้งเดียว และระบบเก็บเฉพาะค่าแฮช SHA-256 ของโทเคน การสร้างโทเคนใหม่จะทำให้โทเคนเดิมใช้ไม่ได้ ต้องอัปเดตการตั้งค่าและเริ่ม Relay ใหม่

3. ติดตั้ง Node เวอร์ชัน 20 ขึ้นไปและ FFmpeg บนเครื่องที่เชื่อถือได้ในเครือข่าย LAN เดียวกับกล้อง จากนั้นตั้งค่าตัวแปรสภาพแวดล้อมต่อไปนี้บนเครื่องนั้น โดยแทนข้อความใน `<...>` ด้วยค่าจริง:

   ```text
   CCTV_PIN_ID=<pin_id>
   CCTV_RELAY_TOKEN=<one-time relay token>
   CCTV_BACKEND_URL=https://your-public-gateway.example
   CCTV_INGEST_URL=rtsp://<media-host-private-vpn-ip>:8554
   FFMPEG_BIN=ffmpeg
   ```

   `<one-time relay token>` คือโทเคนจากขั้นตอนจับคู่ ส่วน `<media-host-private-vpn-ip>` คือ IP ของเครื่อง MediaMTX บน VPN ส่วนตัว เปลี่ยนโดเมนตัวอย่างใน `CCTV_BACKEND_URL` เป็นที่อยู่ HTTPS ของ nginx สาธารณะด้วย

4. รันคำสั่งนี้บนเครื่อง Relay โดยใช้ระบบจัดการบริการที่คุณใช้อยู่:

   ```sh
   node scripts/cctv-relay.cjs
   ```

   Relay จะติดต่อออกไปทุก 5 วินาที ไม่เปิดพอร์ตรอรับการเชื่อมต่อ ดึงเฉพาะการตั้งค่าของกล้องตนเอง และหยุดส่งภาพเมื่อเข้าถึงระบบควบคุมไม่ได้หรือความยินยอมถูกเพิกถอน การเชื่อมต่อควบคุมต้องใช้ HTTPS ยกเว้นการทดสอบผ่าน loopback ภายในเครื่อง FFmpeg รับข้อมูลเข้าสู่ระบบผ่านอาร์กิวเมนต์ของโปรเซส จึงควรจำกัดผู้ที่เข้าถึงเครื่อง Relay และดูรายการโปรเซสได้

5. หากต้องการค้นหากล้อง ONVIF ใกล้เคียง ให้กด **ค้นหา ONVIF** ของกล้องที่จับคู่ Relay แล้ว รอประมาณ 10 วินาที จากนั้นโหลดผลการค้นหา การค้นหาทำงานบน LAN ของ Relay นั้น ไม่ใช่บน backend ที่โฮสต์อยู่ เลือก IP ที่ค้นพบเพื่อแก้ไขกล้องที่จับคู่ แล้วระบุ RTSP path และข้อมูลเข้าสู่ระบบของอุปกรณ์ ระบบค้นหาจะแสดงเฉพาะ IP ยังไม่รองรับการดึงโปรไฟล์สื่อหรือที่อยู่สตรีมจาก ONVIF โดยอัตโนมัติ

   หากต้องการค้นหาก่อนลงทะเบียนกล้องตัวแรก ให้รันคำสั่งนี้จากเครื่องในเครือข่ายกล้อง แล้วใช้ IP ที่ค้นพบในการลงทะเบียน:

   ```sh
   node -e "require('./scripts/cctv-relay.cjs').discover().then(console.log)"
   ```

6. ตรวจสอบเจ้าของกล้องและยืนยันความยินยอมในแบบฟอร์ม งานตรวจสอบสถานะจะสร้างหรือคืนค่าเส้นทางรับสตรีม และตรวจสอบความพร้อมของ MediaMTX ประมาณทุก 15 วินาที เมื่อ Relay ส่งภาพได้สำเร็จ กล้องจะแสดงสถานะออนไลน์ ระบบตรวจสอบจากสตรีมที่ Relay ส่งเข้ามา โดยไม่ส่ง ping จากเซิร์ฟเวอร์เข้าไปยังกล้องในเครือข่ายส่วนตัว

## รายละเอียด API

API ของฟีเจอร์นี้ใช้คำนำหน้า `/api` ตามรูปแบบเดิมของแอป:

- `GET /api/pins/cctv?limit=100&offset=0` และ `GET /api/pins/cctv/:id`: แสดงเฉพาะกล้องที่ผ่านการตรวจสอบและได้รับความยินยอม โครงสร้างข้อมูลตอบกลับ (DTO) มีเฉพาะ `id`, `location: {lat,lng}`, `coverage_direction`, `owner_type`, `status` และ `public_stream_url` กล้องออฟไลน์จะมี URL สตรีมเป็น null ระบบไม่รับ URL สตรีมที่ผู้ใช้กำหนดเอง
- `GET /api/streams/:id`: ส่งกลับ `public_stream_url` ของกล้องที่ออนไลน์ ผ่านการตรวจสอบ และได้รับความยินยอม ตอบกลับ 404 หากกล้องไม่พร้อมให้เข้าถึงหรือไม่ได้รับความยินยอม และ 409 หากกล้องออฟไลน์
- `POST /api/admin/cameras`, `PUT /api/admin/cameras/:id`, `DELETE /api/admin/cameras/:id`: เพิ่ม แก้ไข หรือลบกล้อง รับพิกัด ทิศทาง ประเภทเจ้าของ/การเชื่อมต่อ, `camera_ip`, `rtsp_path`, `credentials: {username,password,port}`, สถานะการตรวจสอบ และความยินยอมของเจ้าของ ระบบปฏิเสธฟิลด์ที่ไม่รู้จักและชนิดข้อมูลที่ไม่ถูกต้อง หากต้องการคงข้อมูลเข้าสู่ระบบเดิมขณะแก้ไข ให้ไม่ส่งฟิลด์ `credentials`
- `GET /api/admin/cameras/:id` และ `GET /api/admin/monitor?limit=9&offset=0`: ส่งข้อมูลสำหรับผู้ดูแล โดยถอดรหัส IP และ RTSP path ให้ แต่จะไม่ส่งข้อมูลเข้าสู่ระบบกล้องหรือค่าแฮชโทเคน Relay กลับมา
- `POST /api/admin/cameras/:id/health`: ปรับสถานะการตั้งค่าสตรีมให้ตรงกันและตรวจสอบความพร้อมทันที
- `POST /api/admin/cameras/:id/relay-token`: สร้างหรือเปลี่ยนโทเคนสำหรับเครื่อง Relay ซึ่งแสดงเพียงครั้งเดียวตอนสร้าง
- `GET /api/admin/cameras/discover?pinId=<id>&refresh=true`: สั่ง Relay ของกล้องนั้นให้ค้นหาอุปกรณ์ในเครือข่าย หากต้องการอ่านผลและสถานะ `pending` ให้ไม่ส่ง `refresh`
- `GET /api/relay/cctv/:id/config` และ `POST /api/relay/cctv/:id/discovery`: สำหรับเครื่อง Relay เท่านั้น ต้องใช้โทเคน Relay ของกล้อง ไม่สามารถใช้ JWT สำหรับเข้าสู่ระบบ รายละเอียดการเชื่อมต่อที่ถอดรหัสแล้วจะส่งให้เฉพาะ Relay ที่จับคู่ถูกต้อง และเฉพาะช่วงที่ความยินยอมยังมีผล
- `/api/internal/cctv/auth`: จุดตรวจสอบสิทธิ์ผ่าน HTTP ที่ MediaMTX เรียกใช้ แยกสิทธิ์สำหรับระบบควบคุม ตัวกลางอ่าน HLS และการส่งภาพของแต่ละกล้อง ปฏิเสธการอ่านหรือส่งภาพที่ไม่มีสิทธิ์ รวมถึงการอ่านภาพผ่าน RTSP
- `/api/internal/cctv/playback/:id`: จุดตรวจสอบสิทธิ์แบบอ่านอย่างเดียวสำหรับ nginx ไม่ส่งข้อมูลกล้องกลับมา

## ความยินยอม การเข้ารหัส และการแคช

ระบบใช้ AES-256-GCM เข้ารหัส IP, RTSP path, ข้อมูลเข้าสู่ระบบ และผลการค้นหากล้อง โดยใช้ค่า nonce ใหม่ทุกครั้ง ซึ่งเป็นค่าที่ช่วยให้การเข้ารหัสแต่ละครั้งไม่ซ้ำกัน ข้อมูลเข้ารหัสแต่ละชุดผูกกับ ID กล้องและชื่อฟิลด์ เพื่อป้องกันการสลับข้อมูลเข้ารหัสระหว่างกล้องหรือฟิลด์

เงื่อนไขในฐานข้อมูลกำหนดให้มีหลักฐานยืนยันความยินยอม ได้แก่ ID ผู้ดูแลและเวลายืนยัน รวมถึงต้องตรวจสอบเจ้าของแล้ว จึงจะเปลี่ยนเป็นสถานะออนไลน์ได้ การแก้ไขข้อมูลการเชื่อมต่อหรือเจ้าของจะยกเลิกความยินยอมเดิม เว้นแต่ผู้ดูแลจะยืนยันใหม่อย่างชัดเจน

เมื่อเพิกถอนความยินยอมหรือลบกล้อง ระบบจะอัปเดตฐานข้อมูลก่อน nginx จะตรวจสอบสิทธิ์ปัจจุบันสำหรับ **ทุกคำขอรายการสตรีมและชิ้นส่วนวิดีโอ** รวมถึงคำขอที่มีข้อมูลอยู่ในแคชแล้ว ไฟล์รายการสตรีม (manifest) จะไม่ถูกแคช ส่วนชิ้นส่วนวิดีโอจะแคชภายในระบบเป็นเวลา 10 วินาที

ข้อมูลตอบกลับไปยังเบราว์เซอร์กำหนดเป็น `no-store` และ service worker จะไม่แคชคำขอเกี่ยวกับกล้อง ผู้ดูแล หรือสตรีม ภาพที่ส่งถึงผู้ชมแล้วไม่สามารถเรียกคืนได้ เครื่องเล่นจะตรวจสอบสิทธิ์ซ้ำทุก 10 วินาทีด้วย การแก้ไขการเชื่อมต่อหรือเปลี่ยนโทเคนต้องตัดผู้ส่งภาพเดิมก่อน จึงจะกลับเป็นออนไลน์ได้ การตรวจสอบหมายเลขรุ่นของข้อมูลช่วยป้องกันไม่ให้งานตรวจสอบสถานะเก่าเขียนทับข้อมูลที่เพิ่งแก้ไข

ตัวกลาง HLS จำกัดจำนวนคำขอและการเชื่อมต่อ API จำกัดขนาดการแบ่งหน้าและมีการจำกัดอัตราคำขอแยกต่างหาก หน้าผู้ดูแลแสดงได้สูงสุด 9 สตรีมต่อหน้า ควรประเมินแบนด์วิดท์และกำลัง CPU ที่ใช้แปลงวิดีโอก่อนเพิ่มจำนวน

## การตรวจสอบและทดสอบ

- รัน `npm run test:cctv` ในโฟลเดอร์ `server`: ทดสอบด้วยคำขอ HTTP จริงผ่าน Express ตรวจสอบ JWT และสิทธิ์จริง แต่ใช้ตัวจำลองของชั้นเข้าถึงฐานข้อมูลและบริการสื่อ การทดสอบครอบคลุมข้อมูลตอบกลับสาธารณะ เส้นทางผู้ดูแลทั้งหมด การแยกสิทธิ์เครื่อง Relay ความยินยอมและการเพิกถอน การเปลี่ยนโทเคน การเข้ารหัส ข้อความผิดพลาดที่ไม่เปิดเผยความลับ และการลงทะเบียนสตรีมแบบส่งออกจาก Relay เท่านั้น
- ตั้ง `TEST_DATABASE_URL` ให้ชี้ไปที่ **ฐานข้อมูล PostGIS สำหรับทดสอบที่ลบทิ้งได้** แล้วรันทดสอบอีกครั้ง เพื่อรวมการทดสอบเงื่อนไขของ migration หากไม่ตั้งตัวแปรนี้ ระบบจะข้ามการทดสอบฐานข้อมูลอย่างชัดเจน และจะไม่ใช้ฐานข้อมูล production
- รัน `npm run build` ในโฟลเดอร์ `client` เพื่อตรวจสอบการบิลด์ React
- ทดสอบเบื้องต้นบนระบบที่ติดตั้งจริง: ลงทะเบียนกล้องทดสอบ จับคู่ Relay ยืนยันความยินยอม และเปิดภาพสด จากนั้นเพิกถอนความยินยอมขณะรับชม แล้วเรียก URL รายการสตรีมเดิม **และ URL ชิ้นส่วนวิดีโอที่มีอยู่ในแคช** ตรวจสอบว่าทั้งสองคำขอถูกปฏิเสธ ลองเริ่ม MediaMTX ใหม่และตรวจสอบว่าเส้นทางสตรีมกลับมาทำงาน จากนั้นเปลี่ยนโทเคน Relay และตรวจสอบว่าผู้ส่งภาพเดิมถูกตัดการเชื่อมต่อ

โครงสร้างฟีเจอร์นี้ไม่ได้จัดเตรียมกล้องจริง VPN หรือบริการสื่อที่เปิดใช้งานแล้วให้ ต้องทดสอบบนสภาพแวดล้อมปลายทางก่อนเปิดเผยแพร่ภาพต่อสาธารณะ
